## 企业知识库 RAG 系统架构设计

> 版本: v1.0 | 日期: 2026-06-22 | 作者: AI Studio 架构组

---

### 1. 背景与目标

企业内部知识文档长期散落在多个系统中——SharePoint、Confluence、钉钉文档、NAS 共享盘、Git Wiki、本地文件夹等。员工查找知识效率低，新入职人员学习成本高，且大量隐性知识随人员流动而流失。

随着 SinoAI Platform 平台的建设，我们有机会将企业知识资产统一汇聚，既服务于人类的知识获取与协作，也为 AI Agent 提供高质量的检索增强生成（RAG）能力。

本方案的核心目标是建设一套 **人机共源** 的企业知识平台——文档只存一份，同时满足人类阅读和 AI 检索两类需求，而非为 AI 单独构建一套封闭知识库。

---

### 2. 设计原则

**人机共源（Single Source of Truth）**：所有文档以原始格式统一存储，人类通过前端阅读原件，AI 的向量索引从同一份文档生成。不存在"人类版本"和"AI 版本"的割裂。

**适配人而非迁移人**：通过连接器从现有系统同步文档，而非要求员工改变习惯将文档"上传到新平台"。系统去适配人的工作方式。

**权限一致性**：AI 检索严格遵守与人类相同的权限控制。没有权限查看某份文档的用户，Agent 也不会将该文档内容作为 RAG 结果返回。

**渐进式建设**：分阶段实施，先跑通核心链路（文档入库 → 向量化 → 检索 → 问答），再逐步扩展连接器、优化质量、丰富功能。

---

### 3. 系统架构

整体采用四层架构，从底向上依次为存储层、处理层、索引层和服务层。

```
┌─────────────────────────────────────────────────────────┐
│                      服 务 层                            │
│  ┌───────────────────┐    ┌──────────────────────────┐  │
│  │   人类访问门户      │    │    Agent API 接口         │  │
│  │  浏览/搜索/协作     │    │  语义检索/上下文获取       │  │
│  └────────┬──────────┘    └───────────┬──────────────┘  │
├───────────┼───────────────────────────┼─────────────────┤
│           │        索 引 层            │                 │
│  ┌────────▼──────────┐    ┌──────────▼──────────────┐  │
│  │   全文索引          │    │    向量索引               │  │
│  │  (Elasticsearch)   │    │  (Milvus / Qdrant)      │  │
│  └────────┬──────────┘    └──────────┬──────────────┘  │
├───────────┼───────────────────────────┼─────────────────┤
│           │        处 理 层            │                 │
│  ┌────────▼───────────────────────────▼──────────────┐  │
│  │          文档处理流水线 (Pipeline)                   │  │
│  │  格式解析 → 智能分块 → Embedding → 索引写入          │  │
│  └────────────────────┬──────────────────────────────┘  │
├───────────────────────┼─────────────────────────────────┤
│                       │       存 储 层                   │
│  ┌────────────────────▼──────────────────────────────┐  │
│  │              文档原仓 (Object Storage)               │  │
│  │     PDF / Word / Markdown / HTML / 代码 / ...       │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

#### 3.1 存储层 — 文档原仓

所有文档以原始格式统一存储，这是整个系统的 truth source。

**存储选型**：MinIO（自建对象存储，S3 兼容）或阿里云 OSS。MinIO 适合内网部署、数据不出域的场景；OSS 适合已使用阿里云生态的团队。

**元数据库**：PostgreSQL，存储文档的元信息（标题、来源、作者、创建时间、所属知识库、权限标签、处理状态等）。元数据与对象存储中的文件通过 URI 关联。

**目录组织**：按知识库（Knowledge Base）作为顶层分区，每个知识库下按来源或业务域划分子目录。示例结构如下：

```
knowledge-store/
├── kb-product-docs/          # 产品文档知识库
│   ├── sharepoint-sync/
│   ├── manual-upload/
│   └── api-generated/
├── kb-tech-docs/             # 技术文档知识库
│   ├── git-wiki/
│   ├── confluence-sync/
│   └── code-docs/
└── kb-internal/              # 内部制度/流程文档
    ├── oa-sync/
    └── dingtalk-docs/
```

#### 3.2 处理层 — 文档处理流水线

文档入库后自动触发处理流水线，依次经过以下阶段：

**格式解析**：将各格式文档转换为结构化文本。PDF 使用 PDF 解析引擎（含 OCR 能力），Word/Excel 通过解析库提取文本和表格，Markdown/HTML 直接解析，代码文件保留结构信息。输出为统一的中间表示（含标题层级、段落、表格、列表等结构标记）。

**智能分块（Chunking）**：将文档拆分为适合向量检索的语义片段。这不是简单的固定 token 数切割，而是根据文档类型选择不同策略（详见第 6 节）。每个 chunk 保留与原文档的关联关系（doc_id、chunk_index、页码/章节定位）。

**Embedding 生成**：对每个 chunk 生成向量表示。推荐使用 BGE-M3 或 text-embedding-v3 等支持中英文的 embedding 模型。向量维度通常为 1024 或 1536。

**索引写入**：将 chunk 文本写入全文索引（Elasticsearch），将向量写入向量数据库（Milvus/Qdrant），同时将权限标签、文档类型、来源等元数据一并写入，供检索时过滤使用。

#### 3.3 索引层 — 双索引并存

**向量索引**（Milvus 或 Qdrant）：服务 AI Agent 的语义检索，支持 top-k 相似度搜索、metadata 过滤。适合"找意思相近的内容"场景。

**全文索引**（Elasticsearch）：服务人类的关键词搜索，支持精确匹配、模糊搜索、高亮显示。适合"找包含某个术语的文档"场景。

实际使用中，推荐 **混合检索（Hybrid Search）**：同时查询两个索引，通过 RRF（Reciprocal Rank Fusion）或加权融合策略合并结果。混合检索的效果通常显著优于纯向量检索，尤其在专有术语、产品型号等精确匹配场景。

#### 3.4 服务层 — 统一入口

**人类访问门户**：提供 Web 界面，支持知识库浏览、文档搜索（关键词 + 语义）、在线阅读/下载、收藏与标注、知识库管理（上传、分类、权限设置）。搜索时定位到具体 chunk，点击可跳转原文并高亮定位。

**Agent API 接口**：为 AI Agent 提供标准化的检索接口。主要接口包括：语义检索（输入 query，返回 top-k 相关 chunks + metadata + 原文链接）、知识库列表与元信息查询、文档详情获取（按 doc_id 返回完整文档内容）。

两个入口查询的是同一份文档、同一套索引，只是呈现方式不同。

### 4. 文档收集策略

企业内部知识散落是最大痛点。采用"三步走"策略逐步汇聚。

#### 4.1 第一阶段：对接已有系统（连接器模式）

通过预置连接器从现有系统定期同步文档，不要求员工改变工作习惯。优先级排序：

| 优先级 | 数据源 | 对接方式 | 预期文档量 |
|--------|--------|----------|-----------|
| P0 | 钉钉文档 | 钉钉开放平台 API | 高 |
| P0 | Git 仓库 Wiki / README | Git webhook + 定时拉取 | 中 |
| P1 | Confluence / Wiki | REST API 全量 + 增量同步 | 中 |
| P1 | SharePoint / OneDrive | Microsoft Graph API | 高 |
| P2 | NAS / 文件服务器 | 文件系统监听 + 定时扫描 | 中 |
| P2 | TFS / 代码文档 | TFS API + 变更集关联 | 低 |

每个连接器需实现：增量同步（只处理变更文档）、格式转换（源格式 → 标准存储格式）、元数据提取（作者、时间、权限信息）、异常处理与重试。

#### 4.2 第二阶段：建立知识入湖标准管道

为新产生的文档提供统一入库通道：

**API 入库**：提供 RESTful API，各业务系统在创建文档时通过 webhook 自动推送。例如审批通过的技术方案自动归档、会议纪要生成后自动入库。

**SDK / 插件**：为常用办公工具提供插件（如 Word 插件、浏览器书签栏工具），一键将当前文档保存到知识库。

**手动上传**：Web 门户支持拖拽上传，作为补充手段。

#### 4.3 第三阶段：质量治理与持续运营

**知识库 Owner 制度**：每个知识库指定负责人，负责审核入库文档质量、定期清理过期内容。

**过期检测**：系统自动标记超过一定时间未更新的文档，提醒 owner 确认是否仍然有效。

**贡献统计**：通过统计面板展示各部门/个人的知识贡献量（文档数、更新频次、被引用次数），形成正向激励。

### 5. 权限与安全模型

#### 5.1 权限架构

采用 **RBAC + 文档级标签** 的混合权限模型。

**知识库级权限**：控制用户能否访问某个知识库。通过角色（管理员、编辑者、查看者）管理，与 LDAP/AD 集成同步组织信息。

**文档级权限**：通过 metadata 标签控制。每份文档在入库时携带权限标签（如 department=R&D, level=internal, team=backend），检索时根据用户身份自动注入过滤条件。

#### 5.2 AI 检索的权限执行

这是企业 RAG 最关键的安全设计。执行链路如下：

```
用户发起查询 → 解析用户身份与权限标签 → 构造检索请求时注入 metadata 过滤条件
→ 向量检索 + 全文检索（仅返回用户有权限的 chunks）→ 结果返回
```

确保权限过滤在检索阶段完成（pre-filtering），而非检索后再过滤（post-filtering），后者会导致返回结果数量不稳定且浪费计算资源。

#### 5.3 数据安全

**传输加密**：所有 API 通信使用 HTTPS/TLS。

**存储加密**：对象存储启用服务端加密（SSE）。

**审计日志**：记录所有文档访问和检索请求，包括谁、什么时间、查询了什么、获取了哪些文档。

**敏感信息过滤**：处理流水线中增加敏感信息检测环节（如身份证号、银行卡号、API Key 等），对高风险文档进行标记或自动脱敏。

### 6. 智能分块策略

Chunk 策略直接影响检索质量，是 RAG 系统最需要精细调优的环节。推荐按文档类型采用不同策略：

| 文档类型 | 推荐分块策略 | 典型 Chunk 大小 |
|----------|-------------|----------------|
| 产品手册 / 用户指南 | 按章节 / Heading 层级切分 | 500-1000 tokens |
| FAQ 文档 | 按问答对切分（Q+A 为一个 chunk） | 200-500 tokens |
| 技术方案 / 设计文档 | 按逻辑段落切分，保留上下文重叠 | 800-1500 tokens，overlap 200 |
| API 文档 | 按接口/方法切分 | 300-800 tokens |
| 代码文档 | 按函数/类/模块切分 | 按代码结构动态调整 |
| 表格密集型文档 | 表格独立成 chunk + 表头上下文 | 整表或按行分组 |

每个 chunk 需携带以下 metadata：所属文档 ID、在原文中的位置（页码/章节/段落序号）、chunk 类型（正文/表格/代码/标题）、权限标签（继承自原文档）。

建议支持 **父子 chunk 关系**：检索时命中子 chunk，但返回给 Agent 时可附带父 chunk（更大范围的上下文），提升回答的完整性。

### 7. 技术选型建议

| 组件 | 推荐方案 | 备选方案 | 说明 |
|------|---------|---------|------|
| 对象存储 | MinIO | 阿里云 OSS | MinIO 适合内网自建，S3 兼容 |
| 元数据库 | PostgreSQL | MySQL | PG 对 JSON 和向量扩展(pgvector)支持好 |
| 向量数据库 | Milvus | Qdrant / pgvector | Milvus 生态成熟，Qdrant 轻量易部署 |
| 全文检索 | Elasticsearch | Meilisearch | ES 功能全面，Meilisearch 轻量快速 |
| 文档解析 | Apache Tika + 自研 | Unstructured.io | Tika 格式覆盖广，自研补充中文优化 |
| Embedding 模型 | BGE-M3 | text-embedding-v3 | BGE-M3 开源可私有部署，支持中英文 |
| 处理流水线 | Celery + Redis | Temporal | Celery 轻量，Temporal 适合复杂编排 |
| 前端门户 | React + Ant Design | Vue + Element Plus | 与 AI Studio 现有技术栈保持一致 |

对于初期规模较小（文档量 < 10 万）的场景，可以简化部署：用 PostgreSQL + pgvector 同时承担元数据库和向量库角色，用 Meilisearch 替代 Elasticsearch，降低运维复杂度。

### 8. 实施计划

整体分为四个阶段，预计 16-20 周完成全部建设。

#### 第一阶段：基础框架搭建（第 1-4 周）

核心目标：跑通"文档上传 → 解析 → 向量化 → 检索问答"的最小闭环。

主要工作包括搭建对象存储和元数据库，实现文档上传与格式解析（PDF、Word、Markdown），集成 Embedding 模型并写入向量数据库，提供基础的语义检索 API，完成 AI Studio 中 RAG 模块的 UI 框架（知识库创建、文档列表、状态展示）。

交付物：可运行的 RAG 基础服务，支持手动上传文档并通过 API 检索。

#### 第二阶段：双通道访问 + 混合检索（第 5-8 周）

核心目标：人类可以像使用知识门户一样浏览和搜索文档，AI 检索质量显著提升。

主要工作包括开发 Web 门户（文档浏览、关键词搜索、在线阅读/下载），部署 Elasticsearch 实现全文索引，实现混合检索（向量 + 关键词 + RRF 融合），优化分块策略（支持按文档类型自动选择），增加 chunk 溯源能力（检索结果附带"查看原文"链接）。

交付物：人类可用的知识库门户，混合检索 API，多种分块策略支持。

#### 第三阶段：连接器 + 权限体系（第 9-14 周）

核心目标：自动从已有系统汇聚文档，权限控制上线。

主要工作包括开发 P0 级连接器（钉钉文档、Git Wiki），开发 P1 级连接器（Confluence、SharePoint），实现 RBAC + 文档级标签权限模型，集成 LDAP/AD 统一认证，实现检索阶段的权限过滤（pre-filtering），建立知识库 Owner 制度和运营管理后台。

交付物：多数据源自动同步，完整权限体系，运营管理后台。

#### 第四阶段：质量优化 + 持续运营（第 15-20 周）

核心目标：持续优化检索质量，建立长效运营机制。

主要工作包括检索质量评估体系（人工评测 + 自动指标），Query 改写与意图识别（提升复杂问题的检索命中率），敏感信息检测与自动脱敏，文档过期检测与自动提醒，贡献统计面板和知识库健康度报告，开发 P2 级连接器（NAS、TFS 等）。

交付物：质量评估报告，敏感信息过滤能力，统计面板，全量连接器上线。

### 9. 关键风险与应对

**检索质量不达预期**：这是 RAG 系统最常见的风险。应对措施是尽早建立评测数据集，持续度量 recall@k 和 precision@k，针对性优化分块策略和 embedding 模型。混合检索通常能显著改善这一问题。

**文档更新不同步**：连接器同步延迟或遗漏。应对措施是设计完善的增量同步机制（基于变更时间戳或 webhook），并提供手动触发重新索引的能力。

**权限泄漏风险**：AI 返回了用户无权查看的文档内容。应对措施是在检索层做 pre-filtering 而非 post-filtering，并定期进行权限合规审计。

**员工参与度低**：知识库建好了但没人用。应对措施是从"搜索入口"切入（集成到钉钉/企业 IM 的搜索框），降低使用门槛；同时通过贡献统计形成正向激励。

---

### 10. 总结

本方案以"人机共源"为核心理念，通过四层架构（存储、处理、索引、服务）构建统一的企业知识平台。文档只存一份，同时服务人类阅读和 AI 检索；通过连接器适配现有系统而非要求员工迁移；通过双索引混合检索保障检索质量；通过 RBAC + 文档级标签确保权限安全。

建议从最小闭环开始（4 周内跑通基础链路），快速验证价值，再逐步扩展数据源和功能。渐进式建设既控制风险，也能让团队在实践中积累经验，做出更符合企业实际需求的系统。
