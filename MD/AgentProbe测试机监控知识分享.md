# Agent Probe 测试机监控：总体架构与实现方案分享

> 本文面向领导和同事，用尽量通俗的方式介绍"测试机空闲探测与监控"这套系统的
> **背景、总体架构、核心实现方案**，以及它给团队带来的价值。

---

## 1. 我们想解决什么问题？

公司内部有一批 Windows 测试机（也是 Jenkins 构建节点），分散在不同位置、由不同同事使用。长期以来存在几个痛点：

- **不知道哪台机器空闲**：要跑测试时，只能一台台远程连上去看，或者问一圈人"这台有人用吗？"
- **状态靠人工维护**：机器被谁占用、什么时候释放，基本靠口头约定，容易冲突
- **机器离线无人知**：某台机器关机、断网了，往往要等用的时候才发现

> **一句话目标：让每一台测试机的实时状态（忙碌 / 空闲 / 离线）自动、实时地呈现在一个页面上，全团队可见。**

---

## 2. 总体思路：给每台机器装一个"探针"

解决方案并不复杂，核心是**三个角色 + 一条自动化下发通道**：

```
┌─────────────────────────── 批量下发通道（Jenkins） ───────────────────────────┐
│  agent-probe 流水线：一条命令，并行下发 install/update/uninstall 到 N 台机器    │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
┌────────────────────────────── ① 探针 Agent（每台测试机） ──────────────────────┐
│  is-busy.py 以 Windows 服务方式常驻（WinSW）                                     │
│  · 开机自启 · 崩溃自动拉起 · 日志自动轮转                                       │
│  · 每 10s 本地采样：键盘鼠标空闲时间 + RDP 会话状态 → 判定 busy / idle            │
│  · 启动即上报 / 状态变化立即上报 / 无变化每 30s 心跳                              │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼ 主动上报
                    POST /api/test-machines/probe（X-Probe-Token 鉴权）
                                    ▼
┌────────────────────────────── ② 后端（SinoAI 平台 FastAPI:8000） ─────────────┐
│  · 校验共享 token → 匹配机器（IP → hostname → 自动注册）                        │
│  · 更新心跳时间与状态（busy / idle / offline）                                   │
│  · 离线守卫：超过 90s 没收到心跳 → 自动置 offline                                │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    ▼
┌────────────────────────────── ③ 前端（测试机管理页面） ────────────────────────┐
│  每台机器卡片：状态徽标（busy/idle/offline）+ 主机名 + 最后心跳时间              │
└──────────────────────────────────────────────────────────────────────────────┘
```

三个关键设计取向：

- **探针主动上报，而不是平台轮询**：机器数量再多也不增加平台压力，新机器装上探针就自动"入网"（自动注册），无需人工登记
- **复用现有平台**：后端不新开端口、复用 FastAPI 8000 和测试机管理页面，前端轻量增强，不改变原有占用/锁定交互
- **一键批量运维**：Jenkins 流水线一条参数，对 N 台机器并行执行安装/更新/卸载/查状态

## 3. 核心实现方案

### 3.1 探针 Agent：怎么判定一台机器"忙不忙"？

基于 Windows 系统 API，两个信号二选一即判定**忙碌**：

| 信号 | 实现 | 含义 |
|------|------|------|
| 键盘/鼠标空闲时间 | `GetLastInputInfo`：距离最后一次键鼠输入过去了多久 | 空闲 < 5 分钟（阈值可配）→ 有人在用 |
| RDP 远程会话 | `WTSEnumerateSessions`：是否有活跃的远程桌面会话 | 有人正远程操作 → 忙碌 |

探针支持三种运行模式：

```
python is-busy.py               # 常驻模式（服务方式运行，无人值守）
python is-busy.py --once        # 单次上报后退出（安装脚本用它验证全链路通不通）
python is-busy.py --status      # 本地打印判定结果（排障用）
```

**健壮性设计**（服务要常年跑，不能轻易挂）：
- 后端不可达时：本地继续采样，不崩溃，指数退避重试（5s → 10s → … → 30s 封顶），恢复后立即补报
- 全部配置走环境变量（服务器地址、token、心跳间隔、空闲阈值…），改配置只需更新服务环境变量，不用改代码
- 自动识别"自己是谁"：取本机 hostname + 与后端通信那块网卡的 IP，多网卡机器也能上报对
- HTTP 只用 Python 标准库（urllib），唯一外部依赖 pywin32，部署成本极低

### 3.2 服务化：像 Windows 系统服务一样常驻

用 WinSW 把探针包装成 Windows 服务（早期用 NSSM，因其在非交互会话下安装不稳定已切换）：

- **开机自启**：机器重启后探针自动恢复上报
- **崩溃自愈**：进程异常退出后 5 秒自动拉起
- **日志轮转**：日志写到 `C:\SinoAI\AgentProbe\logs\`，1MB 自动轮转，不会撑爆磁盘
- **安装/更新/卸载全部脚本化**（`install_probe_service.ps1`），幂等可重复执行

### 3.3 后端：接收上报、维护状态

新增一个端点 `POST /api/test-machines/probe`，探针心跳都打到这里：

1. **鉴权**：共享 token（`X-Probe-Token` 头），与用户登录体系完全隔离——探针是无头服务，不需要也不可能登录。token 比对用恒定时间比较，防时序攻击
2. **机器匹配**：先按 IP 精确匹配 → 再按 hostname 匹配 → 都没有则自动注册新机器（可配置开关）。也就是说**机器零配置入网**
3. **状态计算**：收到上报后按优先级决定展示状态（见第 4 节）
4. **日志克制**：只有状态发生跳变才写一条变更日志，避免每 30s 刷屏

同时新增一个后台"离线守卫"：每 15s 扫一遍，发现某台机器超过 90s（3 个心跳周期）没上报且没被锁定/占用 → 自动置为 `offline`，机器恢复上报后自动回到 busy/idle。**机器挂了，页面 1 分半钟内就能看到。**

### 3.4 状态优先级：谁说了算？

一台机器的最终状态不是探针单方面决定的，规则是**"管理员/用户的操作优先于物理事实"**：

```
locked（管理员锁定）      >  occupied（被占用）      >  busy（物理忙碌）  >  idle
```

- 某同事正在占用（平台"占用"功能）、或管理员锁定了某台机器 → 即使探针上报"空闲"，页面仍显示 busy，不会被覆盖
- 只有真正没人管的状态才跟物理事实走

### 3.5 Jenkins 批量下发：一条流水线管所有机器

新增 `Jenkinsfile.agent-probe` 流水线（2026-09 已随 `DeployScripts/` 迁入内网脚本仓库 `sinounion_scripts/agent-probe-deploy/`），解决"几十台机器一台台装"的问题：

| 参数 | 说明 |
|------|------|
| `AGENTS` | 逗号分隔的目标机器列表（Jenkins 节点名） |
| `ACTION` | install / update / uninstall / status / restart |
| `SERVER_URL` | 后端地址（默认 10.10.11.194:8000） |
| `IDLE_THRESHOLD_SEC` / `INTERVAL_SEC` | 空闲阈值 / 心跳间隔 |
| `PYTHON_PATH` | python 环境差异的兜底项（留空自动探测） |

- **并行下发**：对列表内每台机器开一个并行分支，互不影响，某台失败不拖累其他机器
- **每台机器独立回执**：控制台逐台打印 `RESULT=PASS/FAIL`，一眼定位问题机器
- **安全**：token 走 Jenkins 凭据（Secret text），代码里零硬编码、不打印明文

## 4. 关键设计决策（为什么这么做）

| 决策 | 选择 | 理由 |
|------|------|------|
| 状态采集方式 | 探针主动上报（Push） | 机器数增长平台无压力；自动注册零配置；天然支持"离线"检测 |
| 鉴权方式 | 共享静态 token（内网） | 阶段一够用、部署简单；预留升级路径（每机独立 key / mTLS） |
| 服务化工具 | WinSW（早期 NSSM） | 脚本化、自动重启、开机自启、日志轮转，全生命周期可控 |
| 依赖控制 | HTTP 仅标准库 | 探针只依赖 pywin32，任何机器都能快速部署 |
| 端口 | 复用后端 8000 | 不新开端口，不增加防火墙/nginx 配置面 |
| 数据兼容 | 只加列不删改 | SQLite 幂等迁移，旧数据全保留，回滚零损失 |

## 6. 价值与展望

**给团队带来的直接价值：**
- 测试资源"透明化"：谁在用、哪台空着、哪台挂了，打开页面一目了然，少跑冤枉路
- 机器故障"早发现"：断网/关机 90 秒内页面自动标记离线
- 运维"零手工"：装机、改参数、卸载全部一条 Jenkins 流水线搞定

**后续可以演进的方向：**
- 探针升级为每机独立密钥 / 证书认证（mTLS），进一步加固
- 状态历史曲线：某台机器过去一周的使用率统计，辅助资源规划
- 与占用功能联动提醒：空闲超时自动释放占用等
